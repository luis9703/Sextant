# 新上下文审查：Office/WPS 与 AI、HTML 的需求去向

最扩展原问题的是 **P3「交换能继续用的办法」**。原问题容易被收窄成既有办公人口在 Office 和 HTML 之间换工具，P3 则提出：生成成本下降以后，原先不值得做成软件、甚至不属于传统办公的生活协调，会出现新的生产、分享和维护需求。它改变了需求的来源，而不只是交付格式。这里的“最扩展”是概念判断，不是最可能、最赚钱或最有证据的排名。P5 对工作协调底层对象的改变更激进，但它仍主要围绕既有组织交易。

P3 可更具体为一个虚构的交接事件：社群排班工具作者离开，接手者要改变轮班规则，保留旧记录，说明自己的修改，并在原平台不可用时继续运行。观察对象应是这个交接是否成功、用了多少维护时间、谁承担更新成本，而非“大家生成了很多应用”。还要明确这是原问题外围的新增需求，不直接推断中国知识工作者的套件采购。没有历史采用序列不是否定此未来的理由。

## 事实接地：哪些前提经得住核对

1. **S1 数字正确，但应准确命名口径。** Microsoft FY26 Q4 指标页的 Microsoft 365 Commercial cloud 行显示同比 14%，商业付费席位同比 6%。这里不是整个 Microsoft Cloud 的收入增幅；后者另有一行，Q426 为 27%。中性包已经列出 M365 组织服务的广口径，只是“商业云”简称容易让读者混淆。建议写全名称。该数据支持当前仍有付费需求，不能确定桌面编辑、AI 增量或中国单一市场需求。[Microsoft 原始指标表](https://www.microsoft.com/en-us/investor/earnings/fy-2026-q4/metrics)

2. **S2 收入、增长率和审计边界相符。** 金山办公半年报纸面 p6 披露收入 3,313,262,599.20 元、同比 24.69%，并明确利润增长主要受投资收益影响；重要提示说明未经审计。纸面 p10 的灵犀产品说明确实描述从工作目标出发、规划执行任务并生成可编辑 Office 成果。支持“厂商在尝试吸收迁移”，不构成可靠性交付的实测，也不能把合并收入归因给该产品。[金山办公原始半年报](https://static.cninfo.com.cn/finalpage/2026-08-20/1225482678.PDF)

3. **S3 对网页共存有支持，对共享协商支持不足。** Sway 官方服务页明确写明 Windows Win32 客户端自 2026-06-01 退休，网页及既有内容继续可用。它证明原厂商网页叙事产品的存在；页面所称 interactive canvas 不能直接证明 P2 的多人参数协商、共同模型或计算可靠性。建议把 Sway 保留在呈现层前例，P2 的协商层仍标待验证。[Sway 官方服务说明](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-sway-service-description)

4. **S4 的正文更新可确认，拥有权桥梁不能由它推出。** Anthropic 公告正文有 2025-06-25 日期，以及 2025-10-21 MCP 与持久存储更新；正文描述创建、分享和定制应用。无需依赖导航栏目证明能力。但在平台内可分享、可存储，并不等于作者离开后可继承、离开账号后可运行、规则升级后可迁移。这里是 P3 的互补条件缺口，不是对未来可继承工具的事实反证。[Anthropic 原始公告](https://claude.com/blog/build-artifacts)

5. **S5 使用方式基本克制。** Local-first 论文提出用户控制、离线、协作等理想，并说明其当时考察的数据层未完整满足这些理想。技术一致性或自动合并也不能保证排班规则与社群利益冲突自动解决。保留为技术原则和实验前例，勿变成 2026 通用成熟度或心理需求调查。[Ink & Switch 原文](https://www.inkandswitch.com/essay/local-first/)

没有发现足以删除某条未来路径的已建立硬约束。发现的是证据能力边界、口径措辞与机制之间的缺桥。以下两项新增核对尤其改变 P1/P5 的具体条件。

## P1：保留基础设施化，修订“成熟引擎”的过渡

**挑战与依据。** 从可操作桌面应用直接跳到可扩展后台基础设施，遗漏了运行方式、身份与支持边界。微软官方文档区分无人 RPA 授权与技术支持：桌面 Office 在非交互服务环境会遇到弹窗、身份和并发等问题，并推荐 Graph 或直接操作 Open XML 的替代路线。原生格式需求存在，也不保证必须调用完整桌面 Office。[微软无人自动化考虑事项](https://learn.microsoft.com/en-us/office/client-developer/integration/considerations-unattended-automation-office-microsoft-365-for-unattended-rpa)

**审查推断。** 应把后台分成受支持的组织服务、文件格式处理库、被隔离运行的桌面应用。不同任务落在不同层，收入归属也不同。该文档只约束当前一种实现，不是“未来代理不可后台办公”的结论；未来原厂商可以另建服务接口。

**修复建议。** 为虚构季度报告列出两个交付约束：一是客户仅要可编辑文件；二是客户要求真实套件中的复杂公式、链接和修改往返。在前者，格式兼容库可能足够；后者仍需实际往返测试。观察时同时测人时、后台费用、返工、授权和生成数量。后台调用增长可能由重试或产出膨胀造成，不能单独证明效率或厂商议价权增长。

**人的欲望与失败发展。** 管理者未必愿意取消可见编辑过程，员工也可能要求能看见、能撤回代理修改。若纠错贵，可能形成“代理准备、人逐步确认”的协作，而不只是全自动或人工回流二选一。保留近程窗口；窗口不表示这两类复杂任务都将在其中完成迁移。

**处置与分歧。** 核心保留；后台桥梁和观察指标建议修订。成熟兼容能力能否成为高利润层仍未决，不能凭现有云增长决定。

## P2：保留协商空间，补充参与成本和权力机制

**挑战与依据。** 让人能修改参数与让人愿意公开修改假设是两件事。可信计算层必要，却不能消除领导权、绩效压力或对暴露知识不足的担忧。Sway 和应用生成公告只支持表达工具前例，不能作为协商文化的证据。这里的文化判断是审查假设，未访问会议实测。

**修复建议。** 同一个促销议题可比较“主持人操作、参与者提异议”和“参与者各自直接修改”两种形式。记录一条异议如何进入假设、谁能否决、是否留下不同意见，随后观察共同选择能否执行。这样可区分参与、服从和玩界面。与 Excel 联机模型或 BI 的比较应控制数据、计算与议题，避免把更好模型的效果归给 HTML 或 AI。

**失败开出的方向。** P2 已提出共享核心与个性视图，但共享核心可能被掌权者垄断。进一步可保留多个可比较版本及异议记录，允许暂时不达成一致。若分歧来自利益分配而非理解差异，清晰展示也可能使冲突更尖锐；这不使工具无价值，却改变“共同锁定”的成功定义。人的需求可能是安全表达异议，也可能是尽快结束会议，不能固定为喜欢探索参数。

**处置与分歧。** 保留；对呈现前例的证明力降级，协商过渡建议修订。临时议题是否值得维护模型仍未决，不必强制变为一个新路径。

## P3：保留新增需求，明确“继承了什么”

**挑战与依据。** 当前叙述把工具、规则、运行容器、数据和维护权打包。一个人拿到代码不必然拿到数据，拿到数据也不必然能解释或维护规则；每个社群成员也不必然希望共享私人安排。S4 支持分享应用，S5 支持本地控制原则，均未证明这个完整交接。不能用技术原则填掉人的维护意愿。

**修复建议。** 区分至少三种结果：复制一个不含个人数据的空工具；接管含历史记录的共同工具；改变规则后仍能重放旧决定。排班场景的三个月观察，应记录不迁移的人为什么留下，以及迁移实际人时。停止使用可能因为任务已结束，而不是继承失败；继续运行也可能只因作者持续免费支持，不能单独证明可继承。

**创造挑战。** 原场景把“拥有”与“方便”分叉，但拥有权需求也可能被协作经历塑造：遇到平台涨价或作者退出才开始在意；长期稳定的平台则使交接意愿降低。这是可保留的心理条件，不是已知群体偏好。维护者还可能拥有解释规则的权威，免费社群并不必然更平等。

**失败开出的方向。** 不要仅把维护失败写成退回说明书。工具可冻结执行规则，仅允许替换成员和数值；或社群付费让可信第三方维护，保留可导出的规则和记录。这些是 P3 内部可修复形式，不要求再造新路径，也不保证办公厂商收入增长。

**处置与分歧。** 作为扩大需求来源的条件未来保留；完整继承能力和社群维护意愿未决。生活社群范围应与中国知识工作主范围明确分开。

## P4：保留承诺对象，拆开固定版、手工和信任

**挑战与依据。** “需要一个共同认可的版本”较具体，但不能连带证明“亲自编辑过程更值钱”。自动产生、经人确认并冻结的对象也能形成共同承诺；一份手工制作的报告仍可内容失真。原包已承认 HTML 快照和独立签名等替代，建议把这个非专属性提前到桥梁里。心理机制没有需求访谈，应继续保持假设身份。

**修复建议。** 分别询问使用者要控制内容、保留学习过程、避免版本冲突，还是满足交付规则；比较相同内容下，作者选择记录、冻结状态、可解释计算过程和手工制作标签对引用与支付的影响。它们不能以一个“为固定作品付费”的问题合并测量。新团队偏好固定版也可能来自责任制度，并不自动支持人工掌握的文化需求。

**人的欲望与失败发展。** 一些人会要求自己的技术掌握被认可，另一些人会把掌握代理授权和例外处理看作新身份。后者不必回到传统编辑器，却仍需要看得懂的过程界面。固定与动态可以在同一系统中共存：承诺附在某次决定和数据状态上，其他部分继续更新。原包已保留此分支，值得与学习场景同样充分展开。

**处置与分歧。** 共同承诺的对象保留；人工编辑溢价未决；二者建议拆开。无需因没有心理采用数据而删去远期文化探索，也不能把它包装成套件保底市场。

## P5：保留无文件协调，修订“可撤销”的含义

**挑战与依据。** 跨组织代理可通信的技术前例已经更具体：A2A 规范定义任务、消息、权限和取消请求，但 Cancel Task 明确不保证成功。取消任务也不等于撤回已发送信息、已承诺交易或实物动作。此文档支持互操作结构前例，不证明中国企业已部署自主采购协商或商业责任已解决。[A2A 规范的 Cancel Task 与操作语义](https://a2a-protocol.org/v1.0.0/specification/)

**审查推断与修复。** P5 的必要条件不宜一律叫“可撤销执行”，应区分未承诺提议、授权内的绑定承诺、已经执行但需补偿的动作。虚构的采购场景可以先限定“允许变更的交付时段，无新增金额承诺”；越过边界就交给人。然后逐步考察双方是否愿意为更多自动承诺安排追溯、补偿和责任。逐步授权不是预定的最终路线，只是能检验跃迁的桥梁。

**有边界的经验挑战。** 本次检索发现并访问了一篇代理协商预印本摘要和 PDF：作者报告结构化协议有较好的任务成功表现，同时特定公平分配任务失败较多，并提醒协议保证与模型行为不能混同。但只检查了正文相关方法描述，未复现实验、未核对公开数据代码和全部指标定义；不能用其成功／失败率外推企业未来采用，更不能以负例删除 P5。它作为“要分开测格式合规、达成协议和保全委托人利益”的线索即可。[该研究原文](https://arxiv.org/pdf/2608.14613)

**竞争解释与失败发展。** 不产出文件可能只是不再发附件，真正协调仍由人通过聊天完成；应记录人的例外处理与授权次数。双方也可能并不希望共享真实约束，希望保留谈判空间，这不是简单的数据接通问题。P5 已写渐进披露交涉工具，可更具体为：不同代理提交可接受区间及不可披露项，人比较冲突而不强迫统一语义。它能加强 P2/P4；同时，行业枢纽若统一任务和规则，也可能捕获收入，既非套件必胜也非代理入口必胜。

**处置与分歧。** 较远且不定年的核心保留；撤销与责任桥梁建议修订；无文档端到端协调未验证。协议文档不是业务承诺的替代，现有产品边界也不是未来制度不可改变的证明。

## 跨路径的创造挑战与结论边界

五条路径不是同一个机制换名：P1 改变操作者，P2 改变讨论对象，P3 改变需求人群与继承关系，P4 改变承诺与掌握的价值，P5 改变日常协调的底层对象。其共同出发点确实偏向“生成更便宜”，但无需为了形式上的新颖性再加路径。可以加强现有分叉：内容数量扩大同时可能增加接收者筛选、作者维护和管理者确认的成本；这决定生成需求能否变成可持续服务收入，而非自动成立。

“HTML”更适合作为实现与分发选择，不能单独承担解释。相同 HTML 可是静态快照、参数工具或带账号的应用；相同 Office 文件也可被人工编辑、代理生产或成为冻结承诺。最终判断必须回到任务、直接使用、付款与收入归属，不能给五条路径一个共同的总市场结论。

保留的不确定性包括：中国实际任务分母；不同任务的往返和审阅成本；组织协商的权力条件；社群继承意愿；固定承诺与手工掌握的支付差别；跨组织授权、补偿与谈判保密的制度安排。以上未被本次研究解决。不存在依据把这些未知归为零需求，也不存在依据宣布 Office/WPS 必然继续捕获新增价值。
